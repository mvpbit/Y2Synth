# DrumsRNN Rust autonomous generator (experiment)

This crate contains an offline Magenta.js checkpoint loader, a native Rust three-layer LSTM/attention inference engine, an **autonomous drum-pattern generator**, and a minimal PCM16 WAV preview renderer. It is **not** Y2 firmware or a production drum synthesizer.

The weights must already exist from the repository's `experiments/drumsrnn/download-model.sh`.
The loader reads `config.json`, `weights_manifest.json`, and all referenced binary
shards; checks lengths, tensor names, shape overflow, float32 dtype and finite data;
then decodes actual weights into Rust `Vec<f32>` tensors. A scalar BasicLSTMCell step uses TensorFlow's `i,j,f,o` gate order and runtime `forget_bias=1.0`, with buffers reused across steps.

## Run from the Y2Synth repository root

```bash
cargo test --manifest-path experiments/drumsrnn/rust/Cargo.toml
cargo run --release --manifest-path experiments/drumsrnn/rust/Cargo.toml
```

To override the default checkpoint path:

```bash
cargo run --release --manifest-path experiments/drumsrnn/rust/Cargo.toml -- /path/to/drum_kit_rnn_tfjs
```

Expected for the checkpoint already inspected on Mac:

- 16 tensors
- 2,967,850 float32 elements
- 11,871,400 decoded weight bytes (11.32 MiB)
- attention length 32

**Still not verified:** detailed CPAL live command and long-run behavior, strict real-time safety, controlled runtime benchmarks, cross-compilation, or running on Innioasis Y2. Production drum DSP is not implemented. The WAV renderer is a simple preview, not the final instrument. Loading and decoding all weights uses RAM; embedded suitability has not been established.

The checkpoint-loader tests and LSTM tests use synthetic small matrices; do not mistake a passing unit test for proof of full neural network equivalence. `cargo run --release` loads the real checkpoint and runs **one step per pretrained LSTM layer with a synthetic zero input vector**, which validates finite computations and compatible dimensions, **not a real generated drum event**. Next we need to build the attention wrapper and compare full inference against Magenta.js.

No model weights are committed to Git. `Cargo.lock` for this executable will be
generated by Cargo on the first local build and should subsequently be committed for
reproducible dependency resolution.

## Experimental attention-forward check

The `attention.rs` module follows `magenta-js/music/src/music_rnn/attention.ts`:
- 512 one-hot drum class + 6 signed binary counter values (`-1/+1`, least-significant bit first);
- input projection incorporating previous attention;
- three recurrent 256-wide `BasicLSTMCell` layers;
- 32-slot attention over previous output vectors, queried using all `c/h` states;
- output projection and `512` class logits.

The saved `attention/bias` tensor is loaded and checked but **not applied**
to the attention query, because the original Magenta.js `attention.ts` only
uses `tf.matMul(attnQuery, attnMatrix)` there.

The checkpoint-inspection CLI runs a first forward step after a silent bootstrap and prints the top-five next-class probabilities. **These five probabilities matched Magenta.js to six decimals.** The independent `--bin generate` program additionally makes complete autonomous patterns.

For numerical comparison without exporting JSON, open `reference.html` in **From scratch + Argmax** mode. Both CLI and page display top-five class probabilities on steps 0, 1, 7, 15. The first-step probabilities are independent of later random sampling.

Run:

```bash
git pull --ff-only
cargo test --manifest-path experiments/drumsrnn/rust/Cargo.toml
cargo run --release --manifest-path experiments/drumsrnn/rust/Cargo.toml
```

**Verified on Mac:** the previous 14 tests passed; release loading and three LSTM + attention computations succeeded. Both implementations chose 16 silent classes under Argmax, and the top-five probabilities at steps 0, 1, 7, 15 matched to approximately 1e-6. This is strong evidence of correct multi-step behavior, not a comparison of every one of the 512 probabilities per step.

## Autonomous generation CLI (experimental)

The new `src/generation.rs` and `src/bin/generate.rs` provide a standalone
**from-scratch** 16-step drum generator using the same Magenta checkpoint;
no user-written groove or browser is needed.

```bash
# In the root of the Y2Synth repository
cargo test --manifest-path experiments/drumsrnn/rust/Cargo.toml
cargo run --release --manifest-path experiments/drumsrnn/rust/Cargo.toml \
  --bin generate -- --steps 16 --temperature 1.2

# Deterministic option for comparison with browser's "Argmax":
cargo run --release --manifest-path experiments/drumsrnn/rust/Cargo.toml \
  --bin generate -- --steps 16 --argmax

# Repeat identical pseudorandom sampling within Rust:
cargo run --release --manifest-path experiments/drumsrnn/rust/Cargo.toml \
  --bin generate -- --steps 16 --temperature 1.2 --seed 1234
```

The CLI prints sample time, an ASCII drum-grid, MIDI pitches/steps and
diagnostic top-five next-class probabilities at steps **0, 1, 7, 15**.
Pitch classes match the upstream Magenta default nine drum families:
`[36,38,42,46,45,48,50,49,51]`; class `0` means silence.

The internal **one silent-step seed** is fed to the model once. It is not
part of the output and is not a musician-provided pattern. The generated
class from each step is fed back for the following recurrent step.
`--temperature` samples a categorical distribution, `--argmax` chooses
the most probable class, and `--seed` provides repeatability for Rust.
The Rust sampling RNG is **not identical** to TensorFlow.js's RNG, so
temperature sampling is not expected to match the browser event-for-event.

**Validation status:** Rust loaded the checkpoint and created a 16-step, 9-hit pattern in **40.2 ms** at temperature 1.2 in one Mac test run. Under Argmax, Rust and Magenta.js chose the same 16 classes (all silent), with top-five probabilities matching to around 1e-6 on steps 0, 1, 7, 15. This does not establish full numerical equivalence or hardware performance on Y2.

Model speed on 32-bit ARM, full 512-class numerical equality across all steps, production audio, and Y2 firmware integration remain out of scope.

## Listen to a pattern generated entirely on Rust (new, untested on Mac)

`src/audio.rs` adds a **dependency-free, synthesized WAV preview**.
It turns the existing MIDI-like events into basic kick/snare/hi-hat/tom/cymbal
voices using standard-library math and writes a 44.1 kHz, mono, 16-bit PCM WAV.
This is only for hearing the generated timing, not production DSP.

From the Y2Synth repo root on macOS:

```bash
git pull --ff-only
cargo test --manifest-path experiments/drumsrnn/rust/Cargo.toml

cargo run --release --manifest-path experiments/drumsrnn/rust/Cargo.toml \
  --bin generate -- --steps 16 --temperature 1.2 \
  --wav /tmp/y2synth-groove.wav --bpm 120

afplay /tmp/y2synth-groove.wav
```

No browser, TensorFlow.js, or JSON is involved. The `--wav` argument is
optional, so the original text-only CLI remains unchanged by default.
`--bpm` accepts 40–240 and defaults to 120. Use `--seed` to replay a
specific Rust-generated rhythm. If a sampled pattern has zero hits, the WAV
will contain silence; run the stochastic sampler again.

**Validation status:** new WAV code and its 5 unit tests have been committed,
but have **not yet been compiled or auditioned** on the user's Mac.

## Live drum machine (lock-free revision, Mac verification pending)

An interactive experimental macOS output app has been added:
- portable `src/sequencer.rs` prepares one 16-step PCM loop on the control thread;
- **`src/realtime.rs`** is the actual audio state machine: it owns a `triple_buffer::Output<PreparedLoop>`, an atomic play/stop flag, and a preallocated 15-ms crossfade scratch buffer;
- `src/bin/live.rs` uses `cpal 0.18.2` and `triple_buffer 9.0.0` to deliver precomputed mono samples to the CoreAudio stream;
- model inference, pattern generation, `Vec` creation/replacement and loop rendering are confined to the control thread. On the callback, only bounded memory copy, sample reads and atomic operations are performed.

**Code status:** the user confirmed the triple-buffer live prototype worked on Mac on 2026-11-17. Since then a tunable drum DSP and an Application Controller / menu bridge have been added; **these latest changes have not yet been compiled or auditioned on Mac**. The commands below need rerunning. The `sequencer.rs` module is exported unconditionally; `realtime.rs` and the live binary are enabled by `--features live-audio` and their tests require that feature.

From the Y2Synth repository root:

```bash
git pull --ff-only

# Dependencies are already committed to Cargo.lock in main.
cargo test --locked --manifest-path experiments/drumsrnn/rust/Cargo.toml \
  --features live-audio

cargo run --release --locked --manifest-path experiments/drumsrnn/rust/Cargo.toml \
  --features live-audio --bin live -- --bpm 120 --temperature 1.2
```

Then enter in the interactive terminal:

```text
play
regenerate
bpm 140
stop
play
status
quit
```

`play` starts a repeating 16-step loop, `stop` fades out, `bpm N` prepares the existing groove at a new tempo, and `regenerate` asks the AI for a completely new pattern *without user MIDI input*. New buffers are scheduled on a bar boundary when playback is running. There is no intermediate WAV file.

Current `Cargo.lock` is already committed in `main`. These Application Controller changes require no new dependencies; do **not** commit downloaded model weights or WAV files.

**Real-time caveat:** the rewritten callback no longer uses `std::sync::mpsc` or frees previously active `Vec<f32>` buffers; the `Output<PreparedLoop>` triple buffer switches ownership atomically and old allocations are freed only when the producer replaces its own slot on the control thread. Crossfade samples are copied into a fixed preallocated 15-ms buffer. This remains an experimental design until actual audio dropout/latency/CPU tests on Mac; device routing, CoreAudio behavior, and ARM/Y2Linux compatibility are not yet validated.

## PLAY menu integration (new; needs Mac verification)

`src/ui.rs` models PLAY-first navigation; `src/project.rs` stores three independent typed tracks with shared BPM; `src/application.rs` connects menu commands to the real DrumsRNN, a RAM-only saved snapshot, and `AudioPort`. The synth slots are explicitly unimplemented (not synthetic placeholders).

- AI → Generate Track → Drums generates and queues new PCM using the existing model. The current kit stays intact.
- Returning Home → PLAY queues the latest saved bar and starts playback, **without calling AI again**.
- AI → Generate Track → Synth 1/2 and AI → Generate All return `NotImplemented` and leave the saved project intact.
- Changing `bpm` or `level/tone/decay` preserves the pattern and saves updated settings in memory. All files and DSP work remain on the control thread.

Test the temporary wheel simulator in `live`:

```text
menu
center
next
center
next
center
next
next
center
back
back
back
wheel-play
stop
play
quit
```

`center` selects/enters, `next/prev` changes focus, `back` returns up one level, and `wheel-play` triggers PLAY on Home. Regular `play`, `regenerate`, `bpm` and `kit` commands still work as shortcuts. Session state is saved **only in RAM**; it does not survive closing the process.

Unit tests cover the full menu→AI drums→saved PLAY loop, generation/queue error rollback, kit/tempo preservation and unavailable synth actions. The latest integration still needs actual `cargo test` + audio playback verification on the user's Mac.

## Full numerical validation against Magenta.js: all 16 × 512 probabilities

New portable validator: `src/verification.rs` and `src/bin/verify_reference.rs`. A `generate_with_observer` hook exposes the entire per-step softmax probability vector on the **same inference path** as normal Rust generation. No changes to the live audio callback.

Run from the repository root:

```bash
git pull --ff-only
cargo test --locked --manifest-path experiments/drumsrnn/rust/Cargo.toml
python3 -m http.server 8765 --bind 127.0.0.1
```

Open `http://127.0.0.1:8765/experiments/drumsrnn/reference.html` in a browser. Select **From scratch** and **Argmax**, click **Generate pattern** and then **Save JSON**. The browser should save `drumsrnn-reference.json` (usually to Downloads).

In another terminal (same repository root):

```bash
cargo run --release --locked --manifest-path experiments/drumsrnn/rust/Cargo.toml \
  --bin verify_reference -- \
  --reference "$HOME/Downloads/drumsrnn-reference.json"
```

The program rejects stochastic/primer-based references, invalid probability matrices or wrong checkpoint metadata; checks all 8192 float32 probabilities and all 16 selected class IDs; prints maximum absolute error per step, overall RMS/mean error, worst class, counts above tolerance; exits nonzero on numerical differences. Default per-probability **absolute** tolerance is `1e-5`, adjustable with `--tolerance`.

**Mac Studio verification confirmed on 2026-11-17:** `verify_reference` with exported Magenta.js `@magenta/music@1.23.1` JSON (TF.js WebGL) reported **PASS** for all `16 × 512 = 8192` probabilities. Maximum absolute difference `1.192092896e-6`, mean `1.529578996e-9`, RMS `2.754894988e-8`; `0/8192` values above the `1e-5` tolerance and `0/16` class mismatches. The 16 selected Argmax classes were all zero (silence), so this verifies **one deterministic recurrent trajectory**, not nonzero/forced trajectories, all stochastic input paths, or bitwise equality.


## Forced nonzero history verification (diagnostic mode)

The full 8192-value scratch/Argmax comparison passed on Mac Studio, but its 16 selected classes were all **silent**. A second, independent diagnostic now feeds the **same nonzero previous drum classes** to both implementations and compares *all 512 outputs at every step*.

We deliberately do **not** patch Magenta.js internals or contaminate normal autonomous generation. The browser calls the original `MusicRNN.continueSequenceAndReturnProbabilities(prefix, 1)` for each growing prefix of a fixed 15-class history, starting with one silent bootstrap. Rust's `verification::infer_teacher_forced` runs the same 16-step sequence of recurrent updates. The JSON carries `traceMode: teacher_forced`, 15 `forcedClassIds`, 16 predicted `sampledClassIds`, and `probabilities` (16 × 512). Legacy JSON exports without `traceMode` remain valid.

From the repository root, first start the local server:

```bash
git pull --ff-only
cargo test --locked --manifest-path experiments/drumsrnn/rust/Cargo.toml
python3 -m http.server 8765 --bind 127.0.0.1
```

Open `http://127.0.0.1:8765/experiments/drumsrnn/teacher-forcing.html`, click **Generate 16 × 512 reference** and **Save JSON**.

In another terminal:

```bash
cargo run --release --locked \
  --manifest-path experiments/drumsrnn/rust/Cargo.toml \
  --bin verify_reference -- \
  --reference "$HOME/Downloads/drumsrnn-teacher-forced.json"
```

The default per-value absolute tolerance is `1e-5`. The tool prints the same per-step error matrix and PASS/FAIL as the previous scratch/Argmax verifier, plus the exact forced input class sequence. A PASS confirms numerical agreement **on this one fixed nonzero history**, not on every possible input. **Confirmed on Mac Studio (2026-11-17): PASS.** Magenta.js `@magenta/music@1.23.1` / WebGL vs Rust CPU, `8192/8192` values within absolute tolerance `1e-5`, maximum `1.072883606e-6` (step 15, class 5), mean `2.160613040e-9`, RMS `2.886892393e-8`; zero violations and 16/16 Argmax predictions matched, including nonzero classes. Forced preceding classes: `[5,4,0,6,2,4,8,1,5,20,2,64,4,3,17]`. This confirms one fixed nonzero diagnostic recurrent trajectory, not every possible model state or bitwise identity.


## Synth 1: первый USER-инструмент Pluck / Pad (2026-11-17)

**Статус:** код записан в `main`, на Mac Studio **ещё не скомпилирован и не прослушан**. Это отдельный новый этап после успешно завершённой сверки DrumsRNN (PASS и для тихой, и для ненулевой teacher-forced траектории).

Задача пользователя: отказаться от интерфейса «square / saw» в пользу настоящих музыкальных **пресетов-инструментов**, начиная с **Pluck** и **Pad**.

- `src/synth1.rs`: переносимый USER-синтезатор, пресеты `SynthPreset::Pluck` (шумовое возбуждение затухающей линии задержки, Karplus–Strong-подобный щипковый тембр) и `SynthPreset::Pad` (три слегка расстроенных аддитивных голоса с гармониками, медленной огибающей, движением тембра и вибрато). Нотные события `NoteEvent { step, pitch, length_steps, velocity }`, громкость, два демонстрационных паттерна. Есть тесты параметров, звука, динамики и длительности.
- `src/project.rs` generic-структуру не меняли, но `AppSession` теперь `MusicSession<SynthTrack, UnavailableSynth, DrumTrack>`. AI для Synth 1, Synth 2 и Generate All **не реализован**. USER Synth 1 реально редактируется.
- `src/sequencer.rs::prepare_project_loop`: смешивает заранее рассчитанные mono PCM-бары барабанов и Synth 1 с контролем пика; сохраняет точную drum-only ветку без Synth 1. Публикация PreparedLoop продолжает происходить через triple buffer в границе такта, CoreAudio callback не менялся.
- `src/application.rs`: `set_synth1` публикует новую композицию и сохраняет снимок только после успеха, `PlayLast`, BPM, kit, AI Drums сохраняют имеющийся Synth 1. Добавлены проверки сохранения независимости дорожек и отката на ошибке.
- `src/bin/live.rs`: новые команды для демонстрации, редактирования уровня, нот и отключения мелодии.

## Автономная генерация Synth 1 (2026-11-17; код добавлен, нужен Mac-прогон)

Пользователь уточнил требование: **Synth 1 должен сам генерировать мелодии**, а не только исполнять заранее введённые партии. Реализован отдельный переносимый модуль `src/melody.rs`, не изменяющий тембры Pluck/Pad и real-time callback. Это **музыкальный алгоритм, а не обученная нейросеть**; не называть его ML-инференсом.

- Минорная тональность с несколькими выбранными от seed тониками, гармония i→VI/iv/VII, мотив и ответ из двух половин 16-шагового такта, тональные опорные звуки и умеренная ритмическая вариативность.
- **Pluck:** восемь нот в форме двух связанных мотивов; **Pad:** две четырёхзвучные гармонии по 8 шагов. Сохраняются выбранный `SynthPreset` и уровень USER/AI-трека.
- `RhythmContext::from_drums` использует реальные события kick/snare/hat уже имеющегося `GeneratedPattern`, чтобы выбирать акцентные моменты; с отсутствующей или тихой дорожкой Drums композитор тоже работает.
- В `src/application.rs` добавлен порт `Synth1Generator` и полноценный `dispatch_with_synth` для `Command::GenerateTrack(TrackId::Synth1)`. Новая дорожка публикуется вместе с текущими барабанами в готовом PCM-такте и только после успешного `AudioPort::queue_bar` попадает в RAM-снимок с `CreationMode::Ai`. Генерация не запускает PLAY; воспроизведение сохранённого не вызывает генераторы. `GenerateAll` и Synth 2 пока не реализованы. Предыдущий `dispatch` оставлен для совместимости с Drums-only клиентами.
- `src/bin/live.rs` содержит собственный независимый seed-счётчик мелодий, команду `synth1 generate` и подключение **AI → Generate Track → Synth 1**. Не вмешивается в DrumsRNN seed. Существующие `synth1 pluck` и `synth1 pad` выбирают тембр вместе с DEMO-фразой, после чего `synth1 generate` заменяет ноты новым материалом, сохраняя тембр/уровень.
- Тесты `melody.rs`: фиксированный seed, вариативность, валидные ноты на множестве seeds, два аккорда Pad, влияние ритмического контекста, неверный уровень. В `application.rs`: замена только Synth 1, PLAY без перегенерации, работа без Drums, откат при ошибке генератора/аудиопорта, навигация AI-меню.

**Статус:** исходники закоммичены в `main`, **новая сборка и живое прослушивание на Mac Studio ещё не подтверждены**. Предыдущее успешное пользовательское прослушивание относилось к USER Pluck/Pad, до добавления композитора.
